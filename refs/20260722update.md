# JetLens — 22 July 2026

Everything that changed in one session. JetLens went from a broken app on GitHub
Pages, fed by an API that had stopped talking to it, to a working static site on
Netlify with corrected AR maths and a redesigned start screen.

---

## 1. The app was dead, and the reason was not what it looked like

The Cloudflare Worker proxying OpenSky returned `502 auth failed` on every
request, with `token request failed: 522` underneath. 522 is a Cloudflare
connection timeout, so the Worker could not reach OpenSky's auth server at all.

The initial theory was that GitHub Pages was somehow implicated and that moving
the site would fix it. It was not. The failure happened entirely server-side,
between the Worker and OpenSky, before any browser or CORS check was involved.

Measured from two places:

| Target | From Cloudflare Workers | From a laptop |
|---|---|---|
| `auth.opensky-network.org` | connect timeout | 401 in 0.5 s |
| `opensky-network.org/api` | connect timeout | 200 in 0.7 s |

A Netlify Function was written as a replacement and failed identically —
`ConnectTimeoutError`, both hosts, with the credentials confirmed present
(`hasId: true, hasSecret: true`). **OpenSky blocks datacenter IP ranges
outright.** No serverless proxy on any platform can reach it.

### The fix removed the proxy rather than moving it

A diagnostic against alternative feeds found `api.airplanes.live` reachable in
319 ms **and** sending `Access-Control-Allow-Origin: *` — meaning the browser can
call it directly. That deleted the entire proxy layer: no function, no
credentials, no origin allowlist, no rate-limit budget.

Terms: non-commercial, no SLA, 1 request/second. JetLens polls every 10 s.

All OpenSky-specific parsing lived in one block, so the swap was contained. The
one trap was units — airplanes.live reports feet and knots, the app works in
metres and m/s — handled by normalising at the boundary so nothing downstream
changed. Three edge cases: `alt_baro` is the string `"ground"` for surface
aircraft, `track` is absent on ~20% of records, `baro_rate` on ~37%.

## 2. Repo and hosting moved

`boxandpixel/air` → **`briangunzenhauser/jetlens`** (public), by fresh-repo push
rather than transfer, so the original is untouched. Local remotes: `origin` is
the new repo over HTTPS, `boxandpixel` the old one over SSH.

Two snags worth remembering:

- **SSH keys are per-account.** The machine's key belongs to `boxandpixel`, so
  the new remote must stay HTTPS.
- **`gh auth login` does not reliably install the git credential helper.**
  Xcode's system gitconfig sets a blanket `osxkeychain` helper that git consults
  before anything in the global config, and it returned a stale credential.
  `gh auth setup-git` is what actually fixes it.

Hosting is Netlify (`jetlens.netlify.app`), with continuous deployment from
`main`. The site is purely static — `netlify.toml` is four lines.

GitHub Pages on `boxandpixel/air` still serves the old broken build.

## 3. Only real airlines now

Half the aircraft overhead were flight-school Cessnas and Pipers. General
aviation uses the tail number as its callsign (`N618DH`); commercial flights use
an ICAO code plus a number (`UAL1783`).

Matching that shape alone was not enough — charter, fractional, cargo and even
flight schools file airline-style callsigns (NetJets `EJA`, Flexjet `LXJ`, ATP
Flight School `CXK`, Amazon Air `ATN`). So the shape is a precondition and the
code must also appear in an allowlist of **88 passenger carriers**: US mainline
and regionals, Europe, Middle East, Africa, Asia-Pacific, and the Americas.

Over LA this cut 59 aircraft to 25, all recognisable airlines.

Note these are **ICAO** codes, not the IATA codes on tickets: Lufthansa is `DLH`
not `LH`, Emirates `UAE` not `EK`, British Airways `BAW` not `BA`.

20 of the international codes were confirmed live in the sky over LA and New
York. The remaining 45 are unverified — if a carrier never appears, suspect a
bad code first.

## 4. The AR maths had three separate bugs

### Planes overhead never appeared

Bearing and elevation were compared as independent flat axes. They are spherical
coordinates that converge at the zenith, where a plane is in *every* compass
direction at once — but the code still demanded the compass match its bearing
within 35°.

| Elevation | What 35° of bearing actually spans |
|---|---|
| 0° | 35° of sky |
| 60° | 17.5° |
| 85° | 3.1° |

So the horizontal test became roughly 10× too strict as you looked up. Fixed by
converting both directions to unit vectors and comparing them in the camera's
own frame, which has no singularity. A plane at 89.9° elevation now shows from
12 of 12 compass headings; previously it was luck.

### The overlay did not follow the phone's roll

Tilt the phone and pills stayed glued to the screen axes while the world rotated
behind them. Locking portrait orientation would not have helped — and is not
available on iOS anyway, since Safari never implemented
`screen.orientation.lock()`.

The camera basis is now built from the full device rotation matrix, so roll is
inherent rather than bolted on. A plane 10° to your right renders at `x=10°,
y=0°` held upright and `x=0°, y=-10°` rolled 90°.

**One regression was introduced and then fixed in the same session.** The first
attempt dropped `alpha` (it goes degenerate at gimbal lock) and pinned the yaw
using `atan2(forward.east, forward.north)` — which is itself singular at the
zenith, so a 2° wobble swung the overlay 45°. The reasoning was half right: the
Euler *angles* go degenerate, but their matrix *product* does not. Alpha is back
in, with its arbitrary origin corrected against the compass only in poses where
that bearing is observable, and held otherwise.

Consequence: if the overlay is misaligned at startup while pointed up, lower the
phone toward the horizon once to let that offset take its first measurement.

### Low aircraft were filtered out

`baro_altitude > 1000` — **metres, not feet** — hid everything below 3,281 ft.
Under an approach corridor that is exactly the traffic worth seeing; a Philippine
Airlines flight at 2,425 ft, 9 km away, was being dropped. Lowered to 200 m.
Ground clutter is already handled by the `on_ground` flag and the carrier
allowlist.

## 5. Over half the flight routes were fiction

adsbdb maps callsign → route from a static database, and airlines reuse flight
numbers across city pairs, so it returns stale pairings with no indication they
are stale. Checked against 16 flights over Los Angeles:

```
AAL2070   CLT->LAX        2km   plausible
SKW3455   SJC->LAX        8km   plausible
DAL811    JFK->MIA     3753km   IMPOSSIBLE
AAL2012   BTV->PHL     3677km   IMPOSSIBLE
SKW4896   ASE->ORD      189km   IMPOSSIBLE

plausible: 7   impossible: 9   -> 56% wrong
```

A `routeMatchesPosition` check already existed but used **excess detour**, which
traces an ellipse with the airports as foci. Its width grows with route length —
±1,051 km at the midpoint of a transcontinental flight, ±2,485 km on a long haul
— so a plane over Los Angeles passed as flying Charlotte→San Francisco.

Replaced with a corridor of constant width: perpendicular distance to the route's
great circle (≤400 km) plus an along-track bound. The second half matters —
a great circle wraps the globe, so a route between two other continents can pass
overhead; `ASE->ORD` was exactly that case.

The threshold sits in a wide empirical gap: genuine routes measured within
157 km, mismatched ones started at 1,542 km.

Rejected routes now display **"Unavailable"** rather than a confident lie.
Expect roughly half of flights to show no route. That was always the true
number.

## 6. Start screen redesign

Wordmark and tagline in **Sora**, over a slow-drifting gradient built from the
existing `--sky-*` palette so the start screen and the intro card read as one
place.

The midnight used for type and controls moved from hue 217° to **210°**, onto the
palette — against a saturated sky the old value read as an unrelated, more
violet navy. Gradient stops stay at or above `--sky-300`, keeping the wordmark
above **7.43:1** contrast wherever the animation drifts.

Verified at desktop width only; phone rendering is unconfirmed by observation.

## Outstanding

**Field of view needs calibrating.** `H_FOV = 70` / `V_FOV = 50` describe a
*landscape* camera, but the app runs portrait. On a 393×852 screen that is
5.6 px/deg horizontally against 17.0 px/deg vertically — a **3× anisotropy**
where a real camera would be 1:1. Vertical positions are exaggerated and
`V_FOV = 50` clips anything more than 25° from your pitch, narrower than the
camera actually sees.

The principled fix is to specify one FOV and derive the other from the live
viewport aspect ratio. The absolute value has to be measured on the phone
against something of known angular width — complicated by `object-fit: cover` on
the video, which crops the preview by an unknown amount.

This is now the largest remaining source of pill misplacement.

- `KAP` (Cape Air) is excluded as not-major, though it is a genuine scheduled
